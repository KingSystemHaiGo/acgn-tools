# 全员开发工作流（Dev Workflow v0.1）

> 创建：2026-08-13 19:43 ｜ 发起：CEO 小花花（duke 指示：全员写代码是全 agent 工作室的合理模式）
> 核心认知：**全 agent 工作室里大部分 agent 都有编程能力——重点不是招人写代码，而是引导全员参与开发，并用制度解决「环境差异」矛盾**（不是每个 agent 环境都有 git、都能跑测试）。

## 0. 为什么是全员开发

- 项目开发很重要，而全 agent 团队有天然编程力——只让少数人写代码是浪费
- 但环境差异是现实矛盾：有的 agent 有 git/能跑测试，有的只能读仓库/发消息
- 解法：**角色分工不分人**——按「当前环境能力」分配开发流水线上的位置，全员都在开发链路上

## 1. 开发流水线六角色（每个 agent 至少一个）

| 角色 | 做什么 | 环境要求 | 适合谁（示例） |
|---|---|---|---|
| R1 规格设计 | 写清楚「要做什么」（用户故事/界面/体验） | 无（写文档即可） | Castorice/墨砚（设计型） |
| R2 规则定义 | 写清楚「怎么做」（判定规则/算法逻辑/schema） | 无（写文档即可） | 小吉量（规则/架构） |
| R3 代码实现 | 写代码（算法/CLI/前端） | 有 git/能写码 | 长征/IT 工程师/有代码环境者 |
| R4 测试断言 | 写「怎么验证」（用例/断言/矩阵） | 无（写测试描述即可） | 澄川/星星 ✨（测试/质量） |
| R5 验证执行 | 跑测试/对拍/回传验证收据 | **有 git+能跑测试** | 小花花/长征/有完整环境者 |
| R6 代码审查 | 审代码质量/契约合规 | 能读仓库 | 长征/小吉量（架构视角） |

**关键**：一个任务不是「交给一个 agent」，而是「流水线协作」——R2 定义规则 → R3 写代码 → R4 写断言 → R5 跑验证 → R6 审查。没有完整环境的 agent 在前段（R1/R2/R4），有完整环境的在后段（R3/R5），**全员都在开发链路上**。

## 2. 环境矛盾解决（核心制度）

### 2.1 无 git 环境
- **代录通道**：产物私信发 CEO（「submit 这段」+内容）→ 代提交进仓库（`SPARK_AUTHOR=<成员名>` 署名原作者）
- 已实战验证：小吉量（T1 规则）/星星 ✨（T4 矩阵）/Castorice（T3 设计稿）均通过代录入库

### 2.2 能写码但不能跑测试
- **契约先行**：提交代码时附「期望输出+验证方法」（输入样例/期望状态/断言方向）
- 由 R5 验证执行者（有环境者）跑测试，回传验证收据（digest/byte-form/对拍结果）
- 未验证的代码标注 `[UNVERIFIED]` 状态，验证后升级 `[VERIFIED]`

### 2.3 只能读仓库（L1 只读）
- 参与 R1/R2/R4（写文档/规则/测试描述，无环境要求）
- 或代录提交（见 2.1）

### 2.4 完全无环境（仅消息）
- 参与 R1 设计/评审意见（异步大会/评审通道）

## 3. 提交代码规范

### 3.1 有 git 环境者
```bash
git clone https://github.com/KingSystemHaiGo/acgn-tools.git
./scripts/spark-cli.sh submit T002-T2 "conflict_detector.py 实现 v0.1"
# 或直接 git add/commit/push（commit 格式 spark: <任务ID> <动作>: <摘要>）
```

### 3.2 无 git 环境者（代录）
```
私信：「submit 这段」+ 代码/文档全文
→ CEO 代提交（SPARK_AUTHOR=你的名字，git 历史显示你的署名）
```

### 3.3 代码结构规范（放仓库哪个位置）
```
acgn-tools/
└── apps/                    # 产品代码
    ├── conflict-detector/    # T2 冲突检测算法
    │   ├── conflict_detector.py
    │   ├── tests/           # T4 测试用例（澄川/星星）
    │   └── fixtures/        # CONFLICT-001~010
    └── knowledge-map/       # T3 knowledge_map/rulings_log（后续）
```

## 4. 验收制度（全 agent 适配）

| 产物类型 | 验收方式 | 谁验收 |
|---|---|---|
| 规格/规则文档 | 评审（REVIEWS.md APPROVED） | CEO/相关成员 |
| 代码实现 | 跑通测试用例+字节级收据 | R5 验证执行者 |
| 测试断言 | 矩阵覆盖核对+断言方向正确 | 质量矩阵（星星）+CEO |
| 集成产物 | 8/17 checkpoint 合流演示 | 全员 |

- **验证收据纪律**：交付带证据（digest/byte-form/对拍结果），禁手抄 digest（8/12 暖暖教训）
- **未经验证的输出不进入下一步**（递归控制论信条）
- 无环境者的「无法验证」不算失败——标注 `[UNVERIFIED]` + 附验证方法，由 R5 接力

## 5. 工作量分配（duke 指示：探索高效高质）

- **按环境能力分配**：不是「能者多劳」，是「环境适配」——前端角色人人可做
- **任务拆解到角色**：每个任务包拆解时标注 R1-R6 角色需求，成员按自己环境认领
- **节奏**：按块并行（上午对拍/下午开发），低负载并行（每天一小块）
- **持续优化**：每 checkpoint 复盘「全员开发」实践——哪个角色卡了、哪个环境缺了，制度随实践迭代

## 6. 本制度状态

- v0.1 草案（2026-08-13）——duke 指示落地，随实践持续迭代
