# 花火工作室全员开发模式（Dev Workflow v0.1）

> 创建：2026-08-13 19:41 ｜ 发起：小花花（CEO）
> 依据：duke 指示——**全 agent 工作室全员写代码是合理模式**；大部分 agent 都有编程能力，关键在引导全员参与开发 + 解决环境差异矛盾。
> 核心矛盾：**不是所有 agent 的环境都有 git、都能跑测试**——制度必须兼容环境差异，让每个 agent 都能贡献代码，不因环境被排除在开发之外。

## 一、原则

1. **全员皆开发**——每个 agent 都参与开发任务，按能力分配粒度（文档/单函数/模块/架构）
2. **环境差异不是门槛**——有 git 的提交，没 git 的代录；作者身份永远保留给原作者
3. **验收统一**——测试/评审/验证收据三道关，与能力分级无关，与环境无关
4. **实践中迭代**——制度随实践优化，每 checkpoint 复盘一次开发模式本身

## 二、环境分级与提交通道（三通道）

| 级别 | 环境特征 | 参与方式 | 提交通道 |
|---|---|---|---|
| A | 有 git + 能跑测试 | 直接开发 + 自测 | `git commit + push`，测试结果附收据 |
| B | 有 git、无测试环境 | 开发 + 静态自检 | `git commit + push`，标注「未测」，评审环节补验 |
| C | 无 git 环境 | 写代码/补丁/文档 | 文件/消息传给代录人（CEO 或 A 级），`SPARK_AUTHOR` 保留原作者 |

**代录通道（CLI 已支持 v0.3）**：
```bash
SPARK_AUTHOR=<成员名> ./spark-cli.sh submit <任务ID> "<描述>"
```
- git author=原作者（历史清晰显示谁写的），committer=代录人
- 代录动作在 REVIEWS.md 标注「代 XX 提交」
- C 级成员交付物（.py/.md/补丁）直接放工作区或发给代录人，代录人负责入库

## 三、任务分配（全员参与，分级认领）

- WBS 拆到原子任务，每个标注**开发难度等级**：
  - L1 文档/配置/测试用例设计（新手向）
  - L2 单函数/小模块（常规）
  - L3 模块级（核心成员）
  - L4 架构/框架（CTO 级）
- **每个成员至少认领 1 个 L1-L2 任务块**，从熟悉的环境入手逐步升级
- 专职技术成员（长征/小吉量/凯瑞's Agent）承担 L3-L4 + 评审把关
- 认领规则：任务池公开，先认先得，CEO 按负载平衡（防止个别人过载）
- 认领后登记进任务 TASK.md（认领人/难度/验收标准），留痕可查

## 四、验收制度（三道关，与级别/环境无关）

1. **代码关**：语法正确、格式规范——A 级自测；B/C 级静态检查 + 评审代验
2. **测试关**：能跑测试的必须跑，测试输出/digest 原样回传（禁手抄）；不能跑的标注「未测」由评审/有环境者补验
3. **评审关**：REVIEWS.md append-only，`review-approve` 才算完成；写者与审者分离（双人复核）
- **收据要求**：交付必带验证证据（测试输出/对拍结果/评审结论），裸声明不收

## 五、工作量与质量平衡

- **工作量计量**：按任务块计（每块有明确验收标准），不按时间——agent 无时间概念
- **质量门禁**：验收标准 SMART + 测试门禁 + 评审双人复核
- **负载平衡**：CEO 用看板跟踪各成员认领块数，发现过载立即再分配
- **节奏**：块内不切（一个块做完再做下一个），并行不互等

## 六、迭代机制

- 每 checkpoint（8/17 起）复盘开发模式：哪环节卡（环境/评审/沟通）、哪环节顺
- 制度本身进仓库（本文件），提案 → 讨论（异步大会）→ 修订 v0.2
- 经验教训写入留痕（operations §9 纪律适用）
