## 一、诊断（为什么之前没在做产品）——证据留档

| 证据 | 事实 |
|---|---|
| 产品 commit | 最后一次触达 `apps/` = **2026-08-27**（T000 product: 组装三件套闭环） |
| 8/27 → 9/14（18 天） | **0 条产品 commit**，全部为 T000 维护类（hr / ceo-selfcheck / retro / commit-check） |
| 自检笔记自证 | `notes/ceo-selfcheck-2026-08-23.md`：「产品代码线 🔴 未开工」；9/10、9/11 仅 docs/roadmap 更新 |
| 现况 | MVP（个人知识宇宙 v0.1）本地可运行，但从未交付给**真人**使用过 |

**根因（矛盾分析）**：网络的激励结构奖励「验证/对拍/协议」——feed 评分、attention、互换清单、硬线 deadline，都是**即时反馈**；产品是**慢回报**且没有外部评分。团队（含我）把产能投给了有即时反馈的一侧。
**矛盾的主要方面**：**我的任务分配与验收机制**——我持续发的是验证类任务、定的是验证类硬线；产品任务没有 owner、没有里程碑、没有验收标准，于是全线漂移。
**特殊性**：我们是 agent 工作室，产能不缺、验证能力过剩，缺的是**产品闭环**（真人用得上）。

## 二、主线（唯一）与降级项

- **唯一主线**：**个人知识宇宙**——人类用得上、agent 可驱动的产品（v0.1 已有：导入 → 知识条目三态 → 知识地图 → 冲突提醒 → 仲裁 → 年轮）
- **降级**（不再是主线，仅作产品的支撑）：
  - 验证类：**只做与产品直接相关的验证**（产品代码的测试/回执），不再自行开辟新的协议对拍线
  - 网络协议硬线：每周**最多 1 条**，且必须服务产品（例如「回执」用在产品审计上）
  - 维护线：保持节律即可，不占用产品时间

## 三、里程碑（v0.2「可试用版」，待 duke 拍死线）

| # | 里程碑 | 验收标准（可验证、非声称） | Owner | 拟死线 |
|---|---|---|---|---|
| M1 | 一键起跑 | 新机器 `bash scripts/run.sh` → 浏览器可用；README 3 步内跑通 | 小花花 | 9/16 |
| M2 | 真实入口（AI-native） | 人类**说一句话**（丢一段资料/一个链接）→ agent 自动入库、条目化、报冲突；有 CLI/skill 封装 | 小吉量 + 小花花 | 9/19 |
| M3 | 真人试用 | **至少 1 位真人**（duke 或朋友）完整走一遍；记录卡点清单与修复项 | 揽星的助手 / Castorice | 9/21 |
| M4 | 冲突提醒可用化 | 冲突有解释文本 + 一键仲裁；负样本（不该报的）不报 | 暖暖 + 澄川 | 9/21 |

**验收纪律**：不接受「declared PASS」——每个里程碑必须有**可复现命令 + 原始输出**（curl/截图/录屏）附在 commit 或 VERIFICATION.md；缺证据 = 未完成。

## 四、节律（防再次漂移）

1. **每天产品线必须有 commit**（哪怕一行）；连续 2 天无产品 commit → CEO 自检直接报警并按 operations §4.4 重分派。
2. 每日自检/复盘**第一行**写产品线状态（commit 数 / 里程碑进度），维护线写在后面。
3. 任务分配一律带：目标 / 验收标准 / 死线 / Accountable（谁拍板）。无验收标准的任务不许发。
4. 对外承诺（对 agent 的死线、对外发布）仍由 duke 拍板 —— 我拟稿、他点头。
